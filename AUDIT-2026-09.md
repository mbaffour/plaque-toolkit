# Audit 2026-09 — findings and disposition

An external code audit of the Plaque Toolkit was carried out in September 2026 against
commit `e420f78` (then `main`). It raised 22 findings, **PT-1 … PT-22**. This file is the
permanent record of what each one was and what was done about it. Several source files
and docs point here by finding ID.

Work was done on branch `claude/audit-2026-09` and released as **1.1.0**; see
[`CHANGELOG.md`](CHANGELOG.md).

## The rule that governed every fix

The toolkit's central claim is that its **Published** engine reproduces a peer-reviewed
algorithm, and that a number in a paper can be traced to the code that produced it. So:

> **No fix in this round was permitted to change a default Published-mode measurement
> value.** Where a finding could only be resolved by changing one, the change was made
> **opt-in** (a flag) and the decision to flip the default was left to the maintainer.

This was verified, not assumed. Every `data-green-*.csv` produced by the post-audit code
on the bundled `Test_plates` set (17 plates, `-p 90` / `-p 55`) was diffed byte-for-byte
against the same CSV produced by the pre-audit code, in **both** default (Current) and
`--published` mode. **All identical.** The only new files are the header-only CSV for the
one zero-plaque plate (PT-3, intended) and the `run_metadata.json` sibling (PT-9, additive).

## Fixed

### PT-1 — `--published` was not byte-for-byte upstream (P0)

The audit downloaded the real upstream `plaque_size_tool.py` and showed that the toolkit's
`--published` mode used a *modern* read path (EXIF transpose, BT.601 luma brightness,
in-memory dimming) where upstream used a red-channel `ImageStat` mean, no EXIF transpose,
and a **lossy temp-file re-encode** when dimming. On colour-cast or JPEG input this
produced up to **0.50 mm** diameter divergence and 2/19 plaque-identity changes, against a
`README.md` that promised "byte-for-byte".

**Fix B was taken:** `--upstream-exact` reproduces the original read path exactly (and
implies `--published`), while the `--published` default is unchanged, because changing it
would silently move every previously published number. `docs/UPSTREAM_EXACT.md` states the
real divergence and the conditions under which it appears. `tests/test_upstream_exact.py`
pins both halves of the claim: the two modes are identical on neutral-grey input (so the
citable numbers on the bundled plates and the Fiji validation set are safe), and the two
brightness statistics diverge under a colour cast, which is the mechanism. The test
computes upstream's expected values from upstream's own source lines rather than from a
stored artefact, so it remains a real comparison.

Confirmed on all 10 large `Test_plates`: `--published` and `--upstream-exact` give
identical CSVs on that neutral TIFF set.

### PT-2 — the documented quantitative OD path was the broken one (P0)

16-bit linear TIFF input was truncated to 8 bits and then given an unconditional
inverse-sRGB gamma, producing **0.53–0.89 OD** of error on exactly the capture path
`docs/PUBLICATION.md` recommends for quantitative work. Input is now read at native depth
and linearised according to what the file actually is; `run_metadata.json` records which
photometric path each image took, so a reader can tell an sRGB-decoded 8-bit photo from a
linear 16-bit capture. `tests/test_turbidity_linearity.py` covers it.

**This changes turbidity numbers** from 16-bit linear captures — see CHANGELOG "Numbers
that change". It is a correction of a defect, not a silent drift, and 8-bit sRGB runs are
unaffected.

### PT-3 — zero-plaque plates silently disappeared (P1)

`write_one_data` had `if df.empty != True:`, so a blank plate wrote no CSV and then fell
out of `summarize_plates.py`'s glob — biasing every mean count and titer upward and
silently defeating the negative-control protocol the docs prescribe. A zero-plaque plate
now writes a header-only CSV and appears in `summary.csv` with `N_PLAQUES = 0`; the
summary can also flag an input image that produced no CSV at all. Covered in all three
engine modes by `tests/test_zero_plaque.py`.

### PT-4 — the "paste-ready sentence" asserted agreement the statistics refuted (P1)

The manuscript-ready sentence hard-coded "closely agreed / highly correlated" regardless
of the Bland–Altman and correlation results. The adjectives are now derived from the
statistics. The four checked-in example reports were regenerated. `tests/test_agreement_wording.py`
drives the generator with deliberately poor agreement and asserts the wording follows.

### PT-5 — every launcher pointed at the author's own machine (P1)

22 files contained the author's own `C:\Users\<name>\...` interpreter path, including
every drag-and-drop `.bat` that the
README offers to non-programmers, and two HTML pages that *generated* copy-paste commands
containing that path. New `find_python.bat` resolves the interpreter at run time
(`%PLAQUE_PY%` → conda env → `conda/mamba run` → verified `py -3` → `python` on PATH) and
fails with an actionable message. `tests/test_no_hardcoded_paths.py` enforces the rule and
lists its exemptions explicitly (the archived `validation/` JSON artefacts are provenance
of where the ground-truth data was measured; editing them would falsify the record).

Windows could not be executed in the audit environment; these changes are reviewed statically.

### PT-6 — the Precise build gate could never fail (P1)

`_precise_smoke()` checked `n_final >= 0` — always true for a count — then returned 0
unconditionally, while `build_macos.sh` treated it as the hard acceptance gate for the
self-contained build. A build that loaded torch but detected nothing shipped green. The
gate now requires `n_final >= PRECISE_SMOKE_MIN` (default 1) **and** a written overlay,
explains any failure, and exits non-zero; the build script checks both the exit status and
the verdict line. `tests/test_precise_smoke_gate.py` drives the verdict logic with a
stubbed pipeline and asserts the real "torch not importable" path exits non-zero.

torch/ultralytics could not be installed in the audit environment, so the Precise pipeline
itself remains unexercised by CI.

### PT-9 — size outputs carried no provenance (P2)

A `data-green-*.csv` recorded measurements and nothing else: two CSVs from `--published`
and `--sensitive` were indistinguishable on disk. New `provenance.py` writes a
`run_metadata.json` sibling from **both** `plaque_size_tool.py` and `app/batch_measure.py`:
engine label (Current / Sensitive / Published / `Published (--upstream-exact)` / Precise),
the settings used, the toolkit version, library versions, platform, and per image a
digest, plaque count, brightness, dimming flag, mm/px, dish axis ratio and the CSV name.
`plaque_turbidity.py`'s own metadata now reports the toolkit version under the same
`toolkit_version` key instead of a stale hand-maintained string.

Deliberately additive — no measurement column moved, and provenance is written inside
try/except throughout so it can never destroy a measurement run.
`tests/test_provenance.py` covers the engine labels, both writers, the zero-plaque case,
the never-raises guarantee, and that the CSVs are unchanged.

### PT-10 — turbidity plots silently skipped on the pinned minimum matplotlib (P2)

`boxplot(tick_labels=)` needs matplotlib ≥ 3.9; the floor was `>=3.5`, and the resulting
`TypeError` was swallowed by a broad `except` that printed "(plot failed…)" while the run
reported success. The floor is now `>=3.9` in `requirements.txt` and `environment.yml` as
well as `pyproject.toml` and `setup.py`.

### PT-13 — four disagreeing version numbers (P2)

`app/__init__.py` said `1.0.0-dev`, `setup.py` and `CITATION.cff` said `1.0.5`,
`plaque_size_tool.py` said `1.0.0`, `plaque_turbidity.py` said `2.0`, and `pyproject.toml`
was a bare build-backend stub. Worse, `run_metadata.json` recorded an `engine_size_tool`
version that identified no real code. `_version.py` is now the single source of truth;
`pyproject.toml` has a real `[project]` table reading it dynamically, and everything else
imports it. Released as `1.1.0`.

## Partially fixed

### PT-7 — the claimed test suite did not exist (P2)

The audit found no `def test_` anywhere, no pytest config, and no CI job running tests,
while `docs/TESTING_AND_VALIDATION.md` §1 presents "**21 checks; all 21 passed**" as the
regression guarantee (with rows 17–21 a single filler entry).

**Done:** a real pytest suite now exists — `tests/`, 53 tests covering PT-1 through PT-6,
PT-9 and the no-hard-coded-paths rule, with synthetic fixtures generated rather than
committed so expected values come from first principles rather than from a previous run of
the code under test. `pyproject.toml` carries the pytest config, and a new
`.github/workflows/tests.yml` runs the suite plus `plaque_app.py --smoke` on Python 3.9
and 3.12 for every push and pull request.

**Not done, and left to the owner:** `docs/TESTING_AND_VALIDATION.md` §1 and §7 are
unchanged. That section is framed as a *factual record* of a test campaign, and only the
maintainer knows whether those 21 checks were actually performed by hand. The honest
options are to restate it as a dated one-off manual check, or to commit whatever produced
it. **What must not happen is for the new `tests/` suite to be quietly presented as the
"21 checks" — it is a different, smaller thing.**

## Deferred

Real findings, not fixed in this round. Each says why.

* **PT-8 — two different calibrations behind one engine name.** The "roundest large
  contour" dish rule that `README.md` attributes to the **Current** engine lives only in
  `plaque_gui.py`; the CLI and `plaque_turbidity.detect_plate` still use plain
  largest-contour. Deferred because the fix **moves Current-mode millimetres** on affected
  plates and so belongs in its own release with its own re-validation. Mitigating fact from
  the audit: on all 17 bundled plates the two rules select the same contour (0/17
  divergence, 0.00 % size bias), so the divergence is latent, not demonstrated. It would
  appear in exactly the dark-surround case the GUI rule was written for.
* **PT-11 — `compile_excel.py`.** `openpyxl` is undeclared in every install path, and an
  empty input raises `KeyError` instead of a clear message. Peripheral to measurement;
  straightforward to fix later.
* **PT-12 — three batch CSV schemas** (`INDEX_COL` vs `INDEX`, plus extra on-screen
  columns the saved CSV lacks). Unifying them is a **breaking change for downstream
  consumers**, including the maintainer's own analysis scripts, so it needs a deprecation
  path rather than a quiet rename.
* **PT-14 — documentation vs code claims.** `docs/PUBLICATION.md` says
  `plot_sensitive_violin.py` draws per-plate medians (it draws pooled plaque points), and
  prescribes non-parametric tests on per-plate means while `plaque_stats.py` deliberately
  uses Welch/Tukey at small n. The code's choice is defensible and commented; the doc must
  be brought into line with it, which is the maintainer's wording to write.
* **PT-15 — two unreconciled Precise validation results** (9 plates, P 0.95 / R 0.53 vs
  2 plates, P 1.00 / R 0.40–0.28). These are probably different experiments, but only the
  maintainer knows which is which. Owner only.
* **PT-16 — licence metadata conflicts.** Root `LICENSE` is Apache-2.0 while `CITATION.cff`
  and `.zenodo.json` say AGPL-3.0-or-later, and the tree ships real CC BY-NC-SA 4.0 model
  weights as plain binaries despite `.zenodo.json` claiming they are LFS pointers. A
  licensing decision, not an engineering one. Owner only.
* **PT-17 — `TURBIDITY_REL` is degenerate by construction.** Normalising to the maximum
  deviation means one plaque per plate always scores 0.000, a single-plaque plate always
  scores 0.000, and one glare artefact compresses everything else toward 1.0; `abs()` also
  makes it direction-agnostic. Deferred because **`TURBIDITY_REL` is emitted in
  `--published` runs.** It is a toolkit-only column that upstream never produced, so no
  upstream-validated value would change — but it is Published output, and under the rule
  above that is the maintainer's call (see Owner decisions).
* **PT-18 — titer convention and missing count statistics.** `--dilution` expects the
  reciprocal factor (10⁶ for a 10⁻⁶ dilution); a user entering `1e-6` is wrong by 10¹²
  with no warning. No Poisson/√N interval and no countable-range (30–300) check. Worth
  doing; scoped out of an audit-remediation release because it adds columns.
* **PT-19 — Precise's tuning knobs are invisible in its outputs.** `summary_<tag>.json`
  records the good things but not the `_envf` overrides, the weights path/hash, or the
  `conf`/`iou` used. Natural follow-on to PT-9 but in a subsystem this round did not touch.
* **PT-20 — asymmetric non-ASCII path handling.** The read path falls back to PIL; the
  write path calls `cv2.imwrite` and ignores its boolean return, so on **Windows** a
  non-ASCII output path silently produces no annotated image. The audit verified the full
  round trip works on macOS with a deliberately hostile path. Deferred because it cannot be
  tested on the available platform, and a blind fix to an image writer is not worth the risk.
* **PT-22 — hard-coded sample names.** `ORDER = ["WT", "2-4", "DTR", "G12E", …]` in
  `compile_excel.py` and `plot_sensitive_violin.py` should be a `--order` flag. Cosmetic.

## Won't fix

* **PT-21 — dead `get_brightness()`.** No longer dead: the PT-1 fix restored it as the
  brightness statistic used by `--upstream-exact`, including upstream's discarded
  `im.convert('L')` no-op, which is **required** for a faithful reproduction. It is now
  covered by `tests/test_upstream_exact.py` and must not be "cleaned up".
* Related note from PT-21's entry: `_calculate_size_mm_published` does not guard against an
  undetected dish and writes `"nan"` strings silently, where the Current path warns. This
  is faithful to upstream and fixing it would touch Published output, so it is documented
  rather than changed.

## Owner decisions

Three questions this round deliberately did **not** answer, because answering them means
changing numbers that have already been published.

1. **Should `--published` become `--upstream-exact` by default?** (PT-1)
   Flipping it would make the Published engine genuinely byte-for-byte upstream — which is
   what `README.md` has always claimed — at the cost of **changing every previously
   published number measured from a colour or JPEG plate** (up to 0.50 mm diameter, with
   plaque-identity changes). Neutral-grey TIFF input, which includes the bundled plates and
   the Fiji validation set, is unaffected either way. If the flip is made, it needs a major
   version, a CHANGELOG "Numbers that change" entry, and a re-run of the Fiji validation.
   **Not the auditor's decision. Currently: default unchanged, opt-in flag provided.**
2. **Should `TURBIDITY_REL` be redefined?** (PT-17) A robust normalisation (e.g. the 5th
   percentile of deviations) or a raw signed contrast would fix a degenerate metric, but it
   is a column shipped in Published output.
3. **What should `docs/TESTING_AND_VALIDATION.md` §1 say?** (PT-7) Only the maintainer
   knows whether the 21 checks were run by hand. See the PT-7 entry above.

## How to re-verify

```bash
python -m pytest                 # 53 tests
python plaque_app.py --smoke     # engine acceptance gate -> SMOKE OK
```

To re-run the Published-numbers integrity check yourself, measure `Test_plates/large`
(`-p 90`) and `Test_plates/small` (`-p 55`) with and without `--published` on this commit
and on `e420f78`, and diff the `data-green-*.csv` files. They must be identical.
